1. Introduction🔗

Our goal in writing this guide is to introduce graph theorists to the interactive proof assistant Lean and its associated library Mathlib.

We don't aim to give a comprehensive introduction to Lean for mathematicians: there are many excellent tutorials and texts for this, including:

  • Mathematics in Lean (the definitive introduction to Lean for mathematicians)

  • Theorem Proving in Lean 4 (introduction to interactive theorem proving with dependent types using Lean)

  • A Glimpse of Lean ("an introduction to theorem proving in Lean for the impatient")

  • The Hitchhiker’s Guide to Logical Verification (companion text to a graduate-level course on interactive theorem proving)

  • How To Prove It With Lean (an introduction to proofs in Lean based on the classic textbook)

  • Logic and Proof (a course in logic and proof using Lean)

  • Lean Game Portal (interactive games such as the Natural Number Game)

A first course in graph theory is assumed, as is a basic level of Lean proficiency (for example chapters 1 to 8 of Mathematics in Lean).

Our aim is to give graph theorists an idea of how formalizing their work might look in Lean, making use of Mathlib. In particular we will try to point out the differences that we encounter in Lean, compared to informal definitions and proofs.

1.1. Installation🔗

If you haven't done so already please install Lean and clone a copy of the repository https://github.com/jt496/GraphTheoryInLean.

1.2. How to Read This Guide🔗

If you are reading the .lean files directly in VS Code or similar then see the README.md file for build instructions (lake exe cache get followed by lake build). Each chapter is in a separate folder that also contains any associated exercises.

If you are reading the web version then please note that this is published using Verso. You should be able to see most of the interactive features of Lean such as InfoView messages and #command outputs.

To see the actual output of a #command you need to hover over the #command itself with your cursor (the #command will have wavy underlining). Many terms also have associated doc-strings which you can see by hovering over them; click on them to view their full documentation. Types of terms are also shown. In tactic proofs (i.e. proofs that start with := by) hover over the small lozenge after a tactic to see the proof state at that point, and click it to keep the proof state open (click again to close it).

For example, below you should be able to hover over the #source command to see the verbatim source code of the definition of SimpleGraph in Mathlib. While if you hover over SimpleGraph itself you will see its doc-string; clicking on it will take you to its documentation page. Hovering over the #check will tell you the type of G.Adj u v (it is a Prop), while hovering over u will confirm that it has type V, which in turn you can hover over to see its type Type u_1.

variable {V : Type*} {G : SimpleGraph V} (u v : V) @[ext, aesop safe constructors (rule_sets := [SimpleGraph]), wikidata Q141488] structure SimpleGraph (V : Type u) where /-- The adjacency relation of a simple graph. -/ Adj : V → V → Prop symm : Std.Symm Adj := by aesop_graph loopless : Std.Irrefl Adj := by aesop_graph#source SimpleGraph G.Adj u v : Prop#check G.Adj u v -- Prop SimpleGraph.sum_degrees_eq_twice_card_edges.{u} {V : Type u} (G : SimpleGraph V) [Fintype V] [DecidableRel G.Adj] : ∑ v, G.degree v = 2 * G.edgeFinset.card#check sum_degrees_eq_twice_card_edges -- ∑ v, G.degree v = 2 * G.edgeFinset.card

Throughout this guide we work in the namespace SimpleGraph, so for example Adj means SimpleGraph.Adj, and our definitions get names like SimpleGraph.pathNat₁. When we want to put results or definitions in other namespaces we will do this explicitly.

In the interest of making this guide as readable as possible by graph theorists we introduce quite a lot of "standard" graph theory notation that is not in Mathlib (for example K[n], C[n], K[s, t], Q[n], ω G, χ G, etc.). For reference, see Notation. We also provide lists of the Definitions introduced in the guide and of the main Results proved in it.

1.3. Finding Lemmas🔗

Much of the work of formalizing is finding the right lemma in Mathlib. Mathlib's naming conventions (see Naming Conventions) help, since a name should describe the statement (for example card_neighborFinset_eq_degree), but they only get you so far: the degree of a vertex in a complete graph is complete_graph_degree, not degree_top. So it is worth knowing how to search.

  • The tactic exact? searches Mathlib for a lemma that closes the current goal, and apply? and rw? do the same for apply and rw.

  • Loogle searches by constants and expressions, for example SimpleGraph.degree and SimpleGraph.completeGraph.

  • LeanSearch searches using natural language, for example "degree of a vertex in the complete graph".

  • Mathlib's documentation pages list the declarations of each file in order, so the lemmas about a definition can usually be found near it.

1.4. How This Guide is Structured🔗

This guide is focused entirely on SimpleGraph. We start with the basic definitions in the next chapter before moving on to give many different concrete examples in Constructions. The following chapter, Decidability, Finiteness and Degrees, shows how to compute with graphs and introduces vertex degrees.

The rest of the guide introduces topics mainly according to dependencies in Mathlib: Maps, Cliques, Colorings, Walks, Subgraphs, Connectivity, Distance, Algebraic Graph Theory, before looking at some of the classical Theorems about graphs in Mathlib.

After Maps the guide splits into two strands that can be read in either order: Cliques and Colorings on the one hand, and Walks on the other. The strands meet in Subgraphs, and from there each chapter builds on the previous ones.

Most chapters begin with a few basic sections before moving on to more involved material. Sections or subsections whose titles are marked with a star are more advanced. Later sections sometimes use their results, and recall what they need when they do.

We use three running examples throughout: the n-dimensional hypercube Q[n] (Hypercube), the Mycielskian mμ[G] of a graph G (Mycielskian), and the infinite path pathNat₁ on ℕ (Constructing a SimpleGraph).

Examples of more advanced topics that we cover in the guide include:

  • Graphic Sequences

  • Independence Number of the Kneser Graph

  • Colouring Mycielskians

  • Greedy Colouring

  • Pósa Rotations

  • Bondy–Chvátal Theorem

  • De Bruijn–Erdős Theorem

  • Vertex Connectivity

  • Brooks' Theorem

  • Cut Vertices and Blocks

  • Moore and Cage Bounds

  • Albertson's Precolouring Extension Theorem

  • Counting Copies

  • The Automorphism Group of the Hypercube

  • Kőnig's Theorem

  • Füredi's Stability Theorem

  • Zykov's Theorem

  • Ruzsa–Szemerédi Theorem

Theorems from Mathlib that we survey, mostly in the final chapter Theorems, include:

  • Hall's Marriage Theorem

  • Tutte's Theorem

  • Turán's Theorem and Mantel's Theorem

  • Andrásfai–Erdős–Sós Theorem

  • Erdős–Stone Theorem

  • The Laplacian

  • Strongly Regular Graphs

  • Szemerédi Regularity Lemma

  • Triangle Removal Lemma and Roth's Theorem

  • Kőnig's Lemma and Ends

Each chapter (except this one) has some exercises with worked solutions. Each set of exercises is given first with sorry, and the solutions follow.

Since we want to develop results for our running examples some of these exercises are named lemmas or theorems rather than anonymous examples. To avoid naming clashes we add a prime (foo') to the versions with sorry.

1.6. Use of AI🔗

We used AI tools (Claude and ChatGPT) in the later stages of this project for:

  • Lean code: drafting some definitions and proofs, which we then reviewed and revised.

  • Writing: copy-editing, editorial review (suggesting cuts, reorganization and naming), preparing the bibliography.

  • Figures: creating most of the TikZ diagrams.

  • Tooling: the Lean and Verso customization, together with Python scripts to simplify our conversion process.

The choice of topics and the mathematical exposition are our own.

All the proofs in this guide are checked by Lean, but it can't check that our definitions and statements mean what we claim they mean, or that the prose is correct. We have reviewed everything and take full responsibility for all of it, especially the errors.
